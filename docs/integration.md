## Рантайм и зависимости

Локальное окружение `.venv` создано в папке проекта. Оно использует установленный pywin32 через system-site-packages; SDK MCP и его зависимости установлены внутри `.venv`. Глобальные пакеты не удалялись и не заменялись.

Для чистого окружения на другом разрешённом Windows-компьютере:

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements-integration.lock.txt
```

GAP/OpenServer, лицензия и официальный API установленной версии должны быть предоставлены отдельно. Изменение лицензии, активации или реестра этим проектом не выполняется.

## Проверка предоставленного файла лицензии

При проверке до удаления IPM указанный пользователем `Programnoe_obespechenie/Petroleum Experts IPM 7.5.600/license/License.lic` уже находился в папке установленного IPM. Файлы имели одинаковые размер (1031 байт) и SHA256. В метаданных файла есть продукт `PXGap`; названия OpenServer не обнаружено. Чтение таких метаданных не проверяет подлинность, подпись или права на использование.

Отдельное лицензирование OpenServer начиная с IPM 7.0 прямо указано в официальном установленном `pdf/OpenServer/OpenServer_Complete.pdf`, PDF страница 2. Фактический отказ API — native 22 — сохранён в первичном журнале. Пользователь сообщил, что другой лицензии пока нет; повторный запуск того же теста без изменения настроек не выполнялся.

После переустановки штатный мастер лицензирования доступен как `Licensing Configuration Wizard` (`PxLs.exe`) в меню Petroleum Experts. Когда преподаватель предоставит OpenServer и настройки сервера или аппаратного ключа, их нужно подключить через штатный мастер и подготовить **новый** технический план. Имена полей мастера, формат адреса сервера и переменные окружения здесь не предполагаются. Лицензионные ключи в конфигурацию проекта и журналы помещать не нужно.

Повторить проверку метаданных без запуска GAP можно командой из корня проекта:

```powershell
.venv\Scripts\python.exe scripts/check_license_file.py --license-file '../Programnoe_obespechenie/Petroleum Experts IPM 7.5.600/license/License.lic' --installed-file 'C:/Program Files (x86)/Petroleum Experts/IPM 7.5/License.lic' --output outputs/gap/license_file_check.json
```

Команда выводит только ограниченные метаданные и хеши, не активирует лицензию и не проверяет её через API. Подписи, ключи, hostid и полные строки лицензии в результат не попадают.

## Локальный рабочий процесс

Из корня проекта:

```powershell
.venv\Scripts\python.exe -m gap_integration environment
.venv\Scripts\python.exe -m gap_integration probe
.venv\Scripts\python.exe -m gap_integration prepare-smoke
```

`prepare-smoke` возвращает `plan_id`, хеш, список действий и отдельный путь `outputs/gap/models/<plan_id>.gap`. В GAP пока ничего не записывается. План нужно прочитать. После явного разрешения оператора:

```powershell
.venv\Scripts\python.exe -m gap_integration approve --plan-id <plan_id> --approved-by '<имя оператора>'
.venv\Scripts\python.exe -m gap_integration execute --plan-id <plan_id> --approval-id <approval_id>
```

Эти команды — шаблоны с подстановкой реальных идентификаторов. Не используйте старый терминальный план неудачного теста. При недоступной лицензии повторять один и тот же отказ бессмысленно: сначала нужен доступ к OpenServer.

Запланированный технический тест: создать два JOINT (`AG_J1`, `AG_J2`), соединить их `LINKITEMS` с именем `AG_P1`, сохранить, открыть и считать объекты; второй вызов ensure не добавляет трубу или узлы. `LINKITEMS` сам создаёт PIPE между JOINT–JOINT. Гидравлический решатель не вызывается.

`NEWFILE` и `OPENFILE` заменяют текущую сессию без сохранения. Поэтому worker отказывается создавать модель, если GAP уже запущен. Для экспорта допускается чтение открытого сохранённого файла только при совпадении пути и отсутствии несохранённых изменений. При запуске собственной сессии она закрывается по завершении; при таймауте GAP не объявляется отменённым и не завершается автоматически.

Повтор уже успешного плана возвращает сохранённый результат. SQLite ledger исключает одновременное выполнение и блокирует автоматический повтор при неопределённом исходе. Локальная команда `acknowledge` фиксирует ручной разбор такой ситуации с именем и пояснением; она не запускает повтор старого плана.

## MCP-сервер

```powershell
.venv\Scripts\python.exe -m gap_integration.mcp_server --workspace 'F:\VIBE_CODE\ucheba\agents\AG(AY)ENT'
```

Транспорт — stdio. stdout принадлежит протоколу, диагностические сообщения идут в stderr. Внешний LLM-клиент должен запускать эту команду как дочерний процесс.

Инструменты:

1. `gap_environment` — сведения об окружении, без запуска COM.
2. `gap_probe` — COM и чтение текущего состояния, без создания модели.
3. `gap_prepare_smoke` — подготовить технический план.
4. `gap_prepare_manifest` — проверить манифест и отображение, подготовить производственный план только при готовности.
5. `gap_execute` — выполнить конкретный план при наличии локального receipt.
6. `gap_export` — получить считанный snapshot сохранённой модели внутри проекта.

Локальное подтверждение и разбор UNKNOWN не опубликованы как инструменты LLM. Инструмента для произвольной команды OpenServer нет. Receipt связан с хешем плана; изменение файлов манифеста, mapping или источников после подтверждения обнаруживается.

Проверка настоящего протокола без COM/GAP:

```powershell
.venv\Scripts\python.exe scripts/check_mcp_stdio.py --workspace . --output outputs/mcp_protocol_check.json
```

## Граница готовности

Реализованы `probe`, технический `smoke`, `export` и производственный `build` с предварительной проверкой профиля. Компилятор формирует структурированные операции, а независимый нормализатор получает только прочитанный snapshot. Без утверждённого и проверенного профиля production отклоняется с `UNSUPPORTED_MAPPING` до COM. Наличие кода и модульных тестов не доказывает успешную работу установленного GAP.

Сырой snapshot не выдаётся за нормализованный экспорт первого участника. Чтобы завершить этот этап, после восстановления лицензии нужно:

1. Успешно выполнить изолированный технический тест и сохранить фактический экспорт.
2. На копии модели проверить типы источников/границ, согласованное представление клапанов, геометрию и единицы.
3. Утвердить профиль отображения и параметров, шаблон Enthalpy Balance и реальные доказательства испытаний всех функций профиля.
4. После согласования производственного манифеста выполнить перенос и сравнение GAP-01…09.

Извлечённые технические заметки лежат в `work/gap_inventory/local_api_notes.md`. SDK: https://github.com/modelcontextprotocol/python-sdk (установленная версия зафиксирована в lock-файле).
